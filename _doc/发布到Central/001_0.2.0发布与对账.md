## 3. 一条会让"发布成功"变成假绿的雷（本轮实测，值得所有会话记住）

**`mvn -o deploy -Pcentral` 会静默什么都不发，并且报 BUILD SUCCESS。**

```
$ mvn -o deploy -Pcentral -DcentralBaseUrl=http://127.0.0.1:9      # 假出口预演
[WARNING] Goal publish requires online mode for execution but Maven is currently offline, skipping   ×5（五个模块各一行）
[INFO] BUILD SUCCESS
```

⇒ 加了 `-o`（本仓日常构建习惯就是离线）之后，publish 目标根本不执行，而 Maven 依然绿。
**发布那一遍必须不带 `-o`。**

配套的假出口预演（这才是"发布管道有牙"的证据，两支断言都要过）：

```
$ mvn deploy -Pcentral -DcentralBaseUrl=http://127.0.0.1:9          # 注意：online
[INFO] Using Central baseUrl: http://127.0.0.1:9                    ×5
[INFO] Going to upload .../target/central-publishing/central-bundle.zip
[ERROR] Unable to upload bundle for deployment: Deployment
java.lang.RuntimeException: Invalid request. Connect to http://127.0.0.1:9 [/127.0.0.1] failed: Connection refused
[INFO] BUILD FAILURE                                                 ← 这支要的正是"红"
```

① 产物侧：`central-bundle.zip` 里 **102 条 = 17 件制品 × (正本 + `.asc` + 4 个校验和)**，
五坐标（`z-skill` 的 pom + `api/core/starter/admin` 的 pom/jar/sources/javadoc）**一件不缺、一条外来坐标没有**
（对账脚本在下面 §6；本仓没有任何 `skip*` / `excludeArtifacts` 配置，`grep -n skip --include=pom.xml` 为空）。
② 出口侧：真起了一次 HTTP 上传并被拒 ⇒ 证明它确实在传，而不是"绿色 = 什么都没干"。
`centralBaseUrl` 这个 `-D` 是否真生效，是读插件描述符确认的，不是猜的：
`unzip -p ~/.m2/repository/org/sonatype/central/central-publishing-maven-plugin/0.8.0/*.jar META-INF/maven/plugin.xml`
里 `default-value="https://central.sonatype.com">${centralBaseUrl}`。

同一条描述符还给出另一件：**`<autoPublish … default-value="false">`** ⇒ "validated" 与 "published" 是两态，
BUILD SUCCESS 不代表对外可见。第一趟（`56e7e7e3-…`）就停在这里，所以本仓在 `central` profile 里补了
`<autoPublish>true</autoPublish>`（`pom.xml:208`，与 z-msg / z-schedule / z-graph / z-llm 的写法一致 ——
那四仓各 1 处，`grep -c autoPublish` 实测，本仓原先是 **0** 处）。

## 4. 补上 `autoPublish` 后的第二趟，以及两趟的确切差别

```
$ mvn clean deploy -Pcentral            # 23:34:11 → 23:35:08, BUILD SUCCESS, MVN_EXIT=0
[INFO] Uploaded bundle successfully, deployment name: Deployment, deploymentId: c510866e-4b66-433b-ae2d-8ed729c77606. Deployment will publish automatically
[INFO] Waiting until Deployment c510866e-… is validated
[INFO] Deployment c510866e-… has been validated. To finish publishing visit https://central.sonatype.com/publishing/deployments
```

⚠ **最后那行"手工去点 Publish"是插件的固定模板，不是"这一趟没自动发"的证据** —— 读字节码定的：
`DeploymentPublishedWatcherImpl` 里只有一条 `"Deployment %s has been %s. To finish publishing visit %s/publishing/deployments"`，
而 mojo 的 `<waitUntil … default-value="VALIDATED">`（`plugin.xml:288`）决定了它等到 VALIDATED 就收工，与 autoPublish 无关。
真正区分两态的是 `ArtifactUploaderImpl.toPublishingTypeMessage()`：`PublishingType` 的一个分支印
`require manual publishing`、另一个印 `publish automatically` ⇒ 第二趟那句 **"will publish automatically"** 才是
`autoPublish=true` 生效的证据。两趟差别全在这句上（第一趟印的是"require manual publishing"）。

上传件本身也逐条对过（第二趟的 `central-bundle.zip`，23:34 生成）：**102 条 = 17 件制品 × (正本 + `.asc` + 4 个校验和)**，
`缺 无 / 多 无 / 0.1.2 残留 无`。

发布状态 API 这一趟仍然不可用 —— 两个 deployment id 各查一次，**都返 HTTP 500**
（`{"httpStatus":500,"errorCode":10500,…}`，量具 `~/.cache/zskill_release/deployment_status.py`，
只回显状态不碰凭证）⇒ 与 z-schedule 那仓的实测同症状，**判发没发仍只认 repo1**。

⚠ 本轮我还转述过一条 `Component id "6e3149b5-…" … INVALID_DEPLOYMENT` / `no attachment with extension 'pom'` 报错：
**它在两份归档日志里 `grep -c` 均为 0**（阳性对照 `has been validated` 各 1 命中），也没有第三个 deploy 日志 ⇒

```bash
import zipfile
z = zipfile.ZipFile('target/central-publishing/central-bundle.zip')
actual = set(n.rsplit('/', 1)[-1] for n in z.namelist())
bases = ['z-skill-0.2.0.pom']
for a in ('api', 'core', 'starter', 'admin'):
    bases += ['z-skill-%s-0.2.0.pom' % a, 'z-skill-%s-0.2.0.jar' % a,
              'z-skill-%s-0.2.0-sources.jar' % a, 'z-skill-%s-0.2.0-javadoc.jar' % a]
expected = set(bases) | {'%s.%s' % (b, t) for b in bases
                         for t in ('asc', 'md5', 'sha1', 'sha256', 'sha512')}
print('缺', sorted(expected - actual), '多', sorted(actual - expected))
PY

# 可见后三方对账（repo1 的 .sha256 / 本地 staging / 上传的 bundle 逐件比；17 件全等才算数）
cd z-skill && python3 - <<'PY'
import hashlib, os, subprocess
BASE = 'https://repo1.maven.org/maven2/io/github/yuku123'
STAG = os.path.abspath('target/central-staging/io/github/yuku123')
COORDS = [('z-skill', ['z-skill-0.2.0.pom'])] + [
    ('z-skill-' + a, ['z-skill-%s-0.2.0.%s' % (a, e) for e in ('pom', 'jar', 'sources.jar', 'javadoc.jar')])
    for a in ('api', 'core', 'starter', 'admin')]
sha = lambda b: hashlib.sha256(b).hexdigest()
bad = 0
for c, files in COORDS:
    for f in files:
        remote = subprocess.run(['curl', '-s', '%s/%s/0.2.0/%s.sha256' % (BASE, c, f)],
                                stdout=subprocess.PIPE).stdout.decode().strip()
        local = sha(open(os.path.join(STAG, c, '0.2.0', f), 'rb').read())
        if remote.lower() != local:
            bad += 1; print('FAIL', f, remote[:12], local[:12])
print('不一致=%d' % bad)     # 0.2.0 实测：17 件, 不一致 0
PY

# 验签（外加一支反向对照：改一个字节必须 BAD）
gpg --verify <(curl -s …/z-skill-core/0.2.0/z-skill-core-0.2.0.pom.asc) <(curl -s …/z-skill-core-0.2.0/z-skill-core-0.2.0.pom)
```
